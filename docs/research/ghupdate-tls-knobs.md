# TLS memory knobs reachable on pioarduino precompiled libs

Research for wayfinder ticket #115. Question: which mbedTLS / esp-tls / lwIP memory options are baked into the precompiled arduino-esp32 3.3.11 / ESP-IDF 5.5.5 static libraries that pioarduino ships, and which are adjustable from `platformio.ini` — with an eye on the ~32 KB TLS I/O buffer cost that dominates the OTA heap floor (`ghupdate-mission-notes.md`).

Investigated against the installed packages (`framework-arduinoespressif32` 3.3.11, `framework-arduinoespressif32-libs` 5.5.5+sha.b774170ff46, platform pin 55.03.311 from `platformio.ini:14`), ESP-IDF v5.5 Kconfig, mbedTLS 3.6.6 source, and the pioarduino platform builder scripts. 2026-08-21.

## Verdict

The shipped libs bake in **symmetric 16384/16384 TLS I/O buffers** (`CONFIG_MBEDTLS_SSL_MAX_CONTENT_LEN=16384`, `ASYMMETRIC_CONTENT_LEN` off, `DYNAMIC_BUFFER` off — not even offered, because DTLS is enabled). None of the buffer-size options are `-D`-reachable: they live in compiled code inside `libmbedtls.a`. However, **pioarduino's `custom_sdkconfig` ("Hybrid compile") makes every `CONFIG_MBEDTLS_*` knob reachable from `platformio.ini`** — it rebuilds the IDF static libs locally, so the manual esp32-arduino-lib-builder path is unnecessary. The one *safe* saving is asymmetric buffers with a smaller OUT: **~12 KB per TLS connection for one platformio.ini stanza**. Shrinking IN below 16384 against GitHub's CDN will break with `MBEDTLS_ERR_SSL_INVALID_RECORD`, because nothing in the Arduino client path sends the MFL extension and RFC 8449 record_size_limit is unavailable on both ends.

| Path | What it can change | Realistic saving (this OTA path) | Effort | Notes |
|---|---|---|---|---|
| (a) `build_flags` `-D` only | Nothing in mbedTLS/lwIP memory | **0 KB** | trivial | Buffer sizes are compiled into `libmbedtls.a`; `-D` redefines are ignored/ODR-hazardous ([arduino-esp32 #6286](https://github.com/espressif/arduino-esp32/issues/6286)) |
| (b) pioarduino `custom_sdkconfig` (Hybrid compile) | Any `CONFIG_*`: ASYMMETRIC + OUT_CONTENT_LEN, DYNAMIC_BUFFER (needs DTLS off), lwIP windows | **~12 KB** safe (OUT 16384→4096); up to ~16 KB more from DYNAMIC_BUFFER TX-side, at stability risk | low-med: one ini stanza; first build recompiles the IDF libs (long, needs IDF toolchain download) | The winner. Supported by the pinned platform 55.03.311 (`builder/frameworks/arduino.py:282`) |
| (c) manual espressif/esp32-arduino-lib-builder | Same as (b) | Same as (b) | high: run the lib-builder yourself, repackage, repin | Superseded by (b) — pioarduino automates exactly this |
| (d) `framework = arduino, espidf` (arduino-as-component) | Full menuconfig | Same knobs as (b), plus component-level trimming | high: project restructure, IDF-style build, CI changes | Supported by pioarduino: `arduino.py:456` detects both frameworks and switches Hybrid compile off |
| (e) shrink `IN_CONTENT_LEN` (any path) | — | **do not** | — | GitHub/Fastly sends full 16 KB records; client never advertises MFL; failure is `MBEDTLS_ERR_SSL_INVALID_RECORD` mid-stream |

Recommendation: if the ~36 KB streaming floor from the mission notes ever becomes a real constraint, land `custom_sdkconfig` with `CONFIG_MBEDTLS_ASYMMETRIC_CONTENT_LEN=y` + `CONFIG_MBEDTLS_SSL_OUT_CONTENT_LEN=4096` (the stock ESP-IDF default shape) and accept the one-off lib rebuild in CI. Everything else is poor value.

## What the shipped libs actually bake in

The precompiled libs live in `~/.platformio/packages/framework-arduinoespressif32-libs/esp32/` (`lib/libmbedtls.a`, `libmbedcrypto.a`, `libmbedx509.a`, `libesp-tls.a`). The sdkconfig they were built with ships alongside, and for the plain `esp32` target says:

- `CONFIG_MBEDTLS_SSL_MAX_CONTENT_LEN=16384` — `esp32/sdkconfig:2282` and `esp32/dio_qspi/include/sdkconfig.h:926` (same in `qio_qspi`).
- `# CONFIG_MBEDTLS_ASYMMETRIC_CONTENT_LEN is not set` — `esp32/sdkconfig:2283`. So there are **no separate IN/OUT values**: the ticket's "16384/4096" guess is wrong for this package; it is **16384/16384**. ESP-IDF's `esp_config.h` maps the symmetric value to both `MBEDTLS_SSL_IN_CONTENT_LEN` and `MBEDTLS_SSL_OUT_CONTENT_LEN` only when asymmetric is off (`esp32/include/mbedtls/port/include/mbedtls/esp_config.h:2911-2994`).
- `CONFIG_MBEDTLS_DYNAMIC_BUFFER` — **absent entirely** from the sdkconfig, not even as "is not set". That is because its Kconfig dependency is unmet: `depends on !IDF_TARGET_LINUX && !MBEDTLS_SSL_PROTO_DTLS && !MBEDTLS_SSL_VARIABLE_BUFFER_LENGTH` ([esp-idf v5.5.1 components/mbedtls/Kconfig:100-105](https://github.com/espressif/esp-idf/blob/v5.5.1/components/mbedtls/Kconfig)), and the shipped config has `CONFIG_MBEDTLS_SSL_PROTO_DTLS=y` (`esp32/sdkconfig:2361`). Consequently `MBEDTLS_DYNAMIC_FREE_CONFIG_DATA` and `MBEDTLS_DYNAMIC_FREE_CA_CERT` (the current names; there is no `DYNAMIC_FREE_PEER_CERT` in v5.5 — closest is `FREE_CA_CERT`, Kconfig:129) are also unavailable, since both chain off `MBEDTLS_DYNAMIC_BUFFER` (Kconfig:117-137).
- `# CONFIG_MBEDTLS_SSL_VARIABLE_BUFFER_LENGTH is not set` — `esp32/sdkconfig:2290`.
- `# CONFIG_MBEDTLS_SSL_PROTO_TLS1_3 is not set` — `esp32/sdkconfig:2289`. TLS 1.2 only.
- lwIP, for completeness: `CONFIG_LWIP_TCP_MSS=1436`, `CONFIG_LWIP_TCP_SND_BUF_DEFAULT=5744`, `CONFIG_LWIP_TCP_WND_DEFAULT=5760` (`esp32/sdkconfig:2147-2152`) — all equally baked into `liblwip.a`.
- esp-tls: `CONFIG_ESP_TLS_DYN_BUF_STRATEGY_SUPPORTED=y` (`esp32/sdkconfig:1143`) looks promising but is a red herring — it is a hidden always-`y` capability marker "for external components like OTA, to find out whether the dynamic buffer strategy is supported for particular ESP-IDF version" ([esp-idf v5.5.1 components/esp-tls/Kconfig:117-123](https://github.com/espressif/esp-idf/blob/v5.5.1/components/esp-tls/Kconfig)). The actual strategy field is compiled out: `esp_tls_cfg_t` only contains `esp_tls_dyn_buf_strategy` under `#if CONFIG_MBEDTLS_DYNAMIC_BUFFER` (`esp32/include/esp-tls/esp_tls.h:244`), which is off.

### Compile-time-baked vs header-level

These are all **compile-time-baked, not header-level**. The I/O buffers are allocated inside `libmbedtls.a` (`mbedtls_ssl_setup` → buffer allocs sized by `MBEDTLS_SSL_IN_BUFFER_LEN`/`OUT_BUFFER_LEN`, constants folded into the compiled objects), and the incoming-record length check compares against the compiled-in `MBEDTLS_SSL_IN_CONTENT_LEN` ([mbedtls v3.6.6 library/ssl_msg.c:4301-4305](https://github.com/Mbed-TLS/mbedtls/blob/v3.6.6/library/ssl_msg.c)). Redefining `MBEDTLS_SSL_IN_CONTENT_LEN` via `-D` in `platformio.ini` changes only what *your* translation units see — the library keeps its 16 KB behavior, and structs/offsets can silently diverge. This exact failure ("no effect on memory usage by TLS connections") is on record for arduino-esp32 precompiled libs: [espressif/arduino-esp32 #6286](https://github.com/espressif/arduino-esp32/issues/6286). The same reasoning applies to `CONFIG_MBEDTLS_DYNAMIC_BUFFER` with an extra hazard: defining it via `-D` changes the size/layout of `esp_tls_cfg_t` (`esp_tls.h:244`) relative to the compiled `libesp-tls.a` — an ABI mismatch, not a feature.

Note also that this repo's OTA path (`src/core/GhUpdate.cpp:34`, `BundleClient : public NetworkClientSecure`) never touches esp-tls at all: NetworkClientSecure's `ssl_client.cpp` (`~/.platformio/packages/framework-arduinoespressif32/libraries/NetworkClientSecure/src/ssl_client.cpp:317`) drives raw mbedTLS directly. esp-tls dynamic-buffer strategies, even if enabled, would only help code using `esp_http_client`/`esp_https_ota`, not Arduino `HTTPClient`.

## What pioarduino can change without a manual lib rebuild

The pinned platform (55.03.311) contains pioarduino's **Hybrid compile**: putting `custom_sdkconfig` in the env makes the builder discard the stock precompiled libs and recompile the IDF libs locally with the requested `CONFIG_*` overrides (`~/.platformio/platforms/espressif32/builder/frameworks/arduino.py:282-298` reads the option, `check_reinstall_frwrk()`/`call_compile_libs()` at `arduino.py:404-421` trigger `espidf.py` to rebuild; a hash of the custom options is stored in a generated `sdkconfig.defaults` so rebuilds only happen when the options change, `arduino.py:374-399`). This is the pioarduino-only feature advertised in their README (esp32-solo1/C2 Arduino support "via pioarduino only feature: Hybrid compile", [pioarduino/platform-espressif32 README](https://github.com/pioarduino/platform-espressif32)). So option class (b) — "requires espressif/esp32-arduino-lib-builder custom libs" — collapses into "add lines to platformio.ini and pay a long first build": the platform runs the lib-builder machinery for you.

Arduino-as-IDF-component is also genuinely supported: `arduino.py:454-458` explicitly detects `framework = arduino, espidf` and switches Hybrid compile off in favor of the full IDF build. That path gives full menuconfig control but restructures the project; it buys nothing over (b) for this question.

Caveats for (b): the first build downloads and runs the ESP-IDF toolchain (minutes, not seconds, and CI cache keys change); Hybrid compile force-removes `-Wl,--wrap=log_printf` ("Diagnostics is not supported with HybridCompile", `arduino.py:349`); and a generated `sdkconfig.defaults` appears in the project root (`arduino.py:381`).

## The IN_CONTENT_LEN trap: MFL, record_size_limit, and GitHub's CDN

The ~32 KB cost is two buffers: RX ≈ `IN_CONTENT_LEN` + overhead, TX ≈ `OUT_CONTENT_LEN` + overhead. They are *not* symmetric in risk:

**OUT is free to shrink.** The client controls its own record sizes; mbedTLS errors locally with `MBEDTLS_ERR_SSL_BAD_INPUT_DATA` only if *we* try to send a record bigger than OUT ([mbedtls v3.6.6 ssl_msg.c, `mbedtls_ssl_encrypt_buf`: "Record content ... too large" → `MBEDTLS_ERR_SSL_BAD_INPUT_DATA`](https://github.com/Mbed-TLS/mbedtls/blob/v3.6.6/library/ssl_msg.c)), and HTTP GET requests are tiny. ESP-IDF's own default when asymmetric is enabled is IN 16384 / OUT 4096 ([Kconfig:MBEDTLS_SSL_OUT_CONTENT_LEN `default 4096`](https://github.com/espressif/esp-idf/blob/v5.5.1/components/mbedtls/Kconfig)) — the shipped Arduino libs are actually *fatter* than stock IDF here. `CONFIG_MBEDTLS_ASYMMETRIC_CONTENT_LEN=y` + OUT=4096 saves ~12.3 KB per connection; OUT=2048 (still > max handshake flight for a client with no client cert) saves ~14 KB.

**IN cannot safely shrink.** If the peer sends a (decrypted) record longer than `MBEDTLS_SSL_IN_CONTENT_LEN`, mbedTLS returns `MBEDTLS_ERR_SSL_INVALID_RECORD` ("bad message length", [ssl_msg.c:4301-4305](https://github.com/Mbed-TLS/mbedtls/blob/v3.6.6/library/ssl_msg.c)) — so the verified failure mode is `INVALID_RECORD` (-0x7200) for oversized incoming records; `BAD_INPUT_DATA` is the *outgoing* variant. This is exactly what field reports show when people lower IN below 16384 for OTA: "any value lower than 16384 seems not working. I tried values from 8192 to 16384" → `MBEDTLS_ERR_SSL_INVALID_RECORD` ([esp-idf #4649](https://github.com/espressif/esp-idf/issues/4649)). The mission notes' own stall analysis (`ghupdate-mission-notes.md:98`) confirms GitHub's CDN pushes full 16384-byte records today.

Could the client negotiate smaller records? Two mechanisms exist, neither reachable:

- **RFC 6066 max_fragment_length (MFL)**: compiled in — `esp_config.h:1215` defines `MBEDTLS_SSL_MAX_FRAGMENT_LENGTH` unconditionally — but it is *runtime opt-in*: the extension is only sent if something calls `mbedtls_ssl_conf_max_frag_len()`, and neither Arduino's `ssl_client.cpp` nor `NetworkClientSecure` ever does (grep of `~/.platformio/packages/framework-arduinoespressif32/libraries/NetworkClientSecure/src/` — no hits). And even a patched client only *requests*: mbedTLS documents that lowering IN is "safe only if the other end supports MFL or you know it never sends longer messages" ([Mbed-TLS/mbedtls #2258](https://github.com/Mbed-TLS/mbedtls/issues/2258)); large CDN edges commonly ignore MFL, and there is no server-to-client equivalent at all. Without `MBEDTLS_SSL_VARIABLE_BUFFER_LENGTH` (off, `sdkconfig:2290`) a negotiated MFL wouldn't even shrink the allocation — only the wire records.
- **RFC 8449 record_size_limit**: triply unavailable. In the shipped mbedTLS 3.6.6 port header it is commented out and flagged "currently in development and must NOT be used except for testing purposes", and it "Requires: MBEDTLS_SSL_PROTO_TLS1_3" (`esp32/include/mbedtls/port/include/mbedtls/esp_config.h:1218-1229`) — while TLS 1.3 itself is off in the shipped config (`sdkconfig:2289`). And on the server side, OpenSSL — the stack behind most CDN edges including Fastly's TLS termination — has never implemented RFC 8449; it remains an open feature request since 2019 ([openssl #8187](https://github.com/openssl/openssl/issues/8187), still open per [openssl #27827](https://github.com/openssl/openssl/issues/27827)). So even a custom-built client with TLS 1.3 + RSL would not get smaller records from `objects.githubusercontent.com`; no evidence of Fastly honoring either extension was found, and the 32768-byte stall signature in the mission notes is direct evidence of 16 KB records in practice.

**DYNAMIC_BUFFER, if you want it anyway**: reachable via `custom_sdkconfig` only as a bundle — `CONFIG_MBEDTLS_SSL_PROTO_DTLS=n` (to satisfy the dependency; nothing in the GhUpdate path uses DTLS, but other IDF components in the monolithic libs may care) + `CONFIG_MBEDTLS_DYNAMIC_BUFFER=y` (which auto-selects `ASYMMETRIC_CONTENT_LEN`, Kconfig:103), optionally `MBEDTLS_DYNAMIC_FREE_CONFIG_DATA`/`FREE_CA_CERT` for handshake-peak reduction. During a *streaming* download the RX buffer is permanently full, so the steady-state saving is only the TX side (already captured by OUT=4096) — the win is between connections and during handshake, at the cost of allocation churn on a fragmented 128 KB heap. Poor fit for this device; the mission notes' fragmentation history argues against it.
